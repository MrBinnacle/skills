# Gotchas

- [OBSERVED 2026-08-07] A skippable close step produced absent packets across more than one session.
- [ANTICIPATED] Human-only invocation preserves control but cannot cover interrupts or crashes.
- [ANTICIPATED] A Stop hook fires after ordinary responses, not only at a true session boundary.
- [ANTICIPATED] Model-reported skill telemetry can be incomplete. Label its source honestly.
- [ANTICIPATED] A validator can check represented claims. It cannot prove that the writer represented every claim.
- [OBSERVED 2026-08-10] A `command` probe was never executed, yet its claim kept `verified` and the packet was ACCEPTED. Any unverifiable claim could be laundered by choosing that probe kind. Refusing to execute packet-supplied commands was correct; leaving the status untouched was not.
- [OBSERVED 2026-08-10] The shipped example `receiver_checks` entry was `git status --porcelain`, which exits zero on a dirty tree, a deleted tracked file, and a clean tree alike. The only example check could not fail.
- [OBSERVED 2026-08-10] A narrative sentence quoting a ticket title that contained the word TODO rejected an otherwise valid packet. A scan for placeholders must not punish prose that discusses them.
- [OBSERVED 2026-08-10] Receive mode without `--config` skipped every configured check and still returned ACCEPTED. A verification that an omitted argument switches off is not a verification.
- [ANTICIPATED] The producer commits, then the packet records HEAD. Committing the packet afterwards moves HEAD and makes the packet reject itself. Keep the packet directory out of version control, or produce the packet after the final commit.
- [OBSERVED 2026-08-10] `pytest test_validate_packet.py` collects no tests and reports "no tests ran". The cases run from `if __name__ == "__main__"` and the functions carry no `test_` prefix. The report reads as success while nothing executed. Run the file directly and require its `PASS:` line.
- [OBSERVED 2026-08-12] The ANTICIPATED ordering gotcha above happened twice, in a project that had already documented the order in an always-loaded file. Prose does not hold it: the close and the packet are two separately typed commands, and whoever types the second cannot see the effect of the first. The packet then rejects itself in the NEXT session, which is the worst place to find out. Fixed by making the requirement declarable — `close_commit.pattern`, checked in produce mode. A constraint a human has to remember is the defect; a louder reminder is not the fix.
- [ANTICIPATED] `close_commit.contains` establishes that HEAD is *a* close commit, not that it is *this* session's. A session that committed nothing sits on the previous close and passes produce mode. Closing that needs a session boundary the validator does not have. Revisit if: the packet directory is consulted for a HEAD an earlier packet already claimed, which would make a stale close detectable.
- [ANTICIPATED] The key is `contains`, not `pattern`, and the name is doing work. It is a literal substring test, so a project that reads "pattern" and writes `"^RITUAL:"` gets a check that matches nothing and refuses every packet forever — a guard that fails closed on everything looks identical to a broken workflow.
- [OBSERVED 2026-08-23] The origin failure recurred, independently, sixteen days and roughly twenty-eight sessions after it was first recorded. A session ran outside the boundary pair entirely — the operator opened the working directory in a different repository and drove the work with another flow — and closed with no packet produced. The next session had to resume from the durable checkpoint instead. This is not fan-out from the 2026-08-07 occurrence: different repository, different cause path, a separate session weeks later. It is the same defect the origin names, and it is the defect the skill does not fix: a step a human must remember to type is a step that gets skipped whenever the session's shape is unusual. The `[ANTICIPATED]` note about interrupts and crashes did not anticipate this shape — the session did not crash, it simply never entered the pipeline.
- [OBSERVED 2026-08-23] First real cross-boundary cutover, from the producer side. A packet written at one session's close was accepted at the next session's cold start with all repository checks green. Two claims the producer had labelled `unverified` were false when the receiving session checked them at source. The labelling was correct and the discipline held, but note what it means for the producer: **`unverified` is doing real work in this format, and a producer that labels generously is safe while one that labels optimistically is not.** When in doubt at close, write `unverified`.
- [OBSERVED 2026-09-06] A first merge attempt for issue #84 added `write_state.py` as a second public script beside `snapshot_state.py` and claimed the order was "structural". It was not: two CLIs the agent must sequence is the same defect as two slash commands the operator must sequence. Fixed by one public entrypoint (`close_session.py`) that writes state, commits, and snapshots inside one process. The open side likewise needs one entrypoint that loads state into the acceptance receipt (`open_session.py`); validating alone drops the doctrine half.
