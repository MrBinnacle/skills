# Craft floor for text written to Linear

Read this immediately before a write that creates or edits an issue, project, milestone, document or status update. Do not read it for read-only work.

## Incumbent conventions first

The workspace's existing labels, templates, workflow states and naming patterns are the incumbent. Match them before you apply anything below. A refinement keeps them. Replace a convention only when the request explicitly asks for a restructure.

## What good looks like

- **Planning:** a person who has not seen the conversation can pick up the project and start. The outcome, scope, exclusions and acceptance criteria are on the project, not in the chat.
- **Operating:** after a triage or queue pass, each issue has one state, one owner where grounded, and a next action.
- **Reporting:** a stakeholder can act on the status update without asking a follow-up question.

## Floor

- **Issue title:** short and simple, and it states the task directly. It must read clearly on a list or board beside other issues. ([Linear Method: write issues](https://linear.app/method/write-issues-not-user-stories))
- **Issue body:** the task has a clear, defined outcome. Write only as much as the assignee and team need. ([same](https://linear.app/method/write-issues-not-user-stories))
- **Project:** state the outcome and the exclusions (non-goals). If the workspace has no scoping convention, Linear's method recommends a project that 1–3 people can finish in 1–3 weeks, split into stages when it cannot be scoped down. Treat that as a recommendation, not a rule. ([Linear Method: scope projects](https://linear.app/method/scope-projects))
- **Status update:** give a health indicator (On track, At risk or Off track), a concise overview of progress since the last update, the challenges, and the next steps. ([Linear docs: project updates](https://linear.app/docs/initiative-and-project-updates))

## Never

- Never write an issue whose title does not say what the task is.
- Never create an issue that is not a task with a defined outcome. Put the observation in an existing issue or project description instead.
- Never create a project, label or milestone before the search and the deletion test in [project-method.md](project-method.md).

## Bounded verification

Read the written objects back once. Fix every gap the read-back shows in one batch. Read the fixed fields back once more, then stop and report any gap that remains.
