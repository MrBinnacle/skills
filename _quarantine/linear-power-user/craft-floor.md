# Craft floor for text written to Linear

Read this immediately before any write that puts text into Linear: an issue, comment, project, initiative, milestone, document or status update. Do not read it for read-only work.

## Incumbent conventions first

Judgement, no source.

The workspace's existing labels, templates, workflow states and naming patterns are the incumbent. Match them before you apply anything below. A refinement keeps them. Replace a convention only when the request explicitly asks for a restructure.

## What good looks like

Judgement, no source.

- **Planning:** a person who has not seen the conversation can pick up the project and start. The outcome, scope, exclusions and acceptance criteria are on the project, not in the chat.
- **Operating:** after a triage or queue pass, each issue has one state, one owner where grounded, and a next action.
- **Reporting:** a stakeholder can act on the status update without asking a follow-up question.

## Floor

- **Issue title:** short and simple, and it states the task directly. It must read clearly on a list or board beside other issues. ([Linear Method: write issues](https://linear.app/method/write-issues-not-user-stories))
- **Issue body:** write it "clear enough so that the assignee can perform it" and give "enough context so that teammates who need to know understand what work is being done". Write only as much as you need to perform the task and communicate relevant information to the team. ([same](https://linear.app/method/write-issues-not-user-stories))
- **Project:** state the outcome and the exclusions (non-goals). That part is judgement, no source. If the workspace has no scoping convention, Linear's method recommends a project that 1–3 people can finish in 1–3 weeks, split into stages when it cannot be scoped down. Treat that as a recommendation, not a rule. ([Linear Method: scope projects](https://linear.app/method/scope-projects))
- **Status update:** give a health indicator (On track, At risk or Off track) and a description of status, challenges and next steps. ([Linear docs: project updates](https://linear.app/docs/initiative-and-project-updates))

## Never

Judgement, no source, for all three rules.

- Never write an issue whose title does not say what the task is.
- Never create an issue for a vague observation with no next action. Put it in an existing issue or project description instead.
- Never create an object before the search for existing work and the deletion test in [project-method.md](project-method.md).

## Bounded verification

Judgement, no source.

Read the written objects back once, as a fresh query. Fix the gaps it shows in one batch, inside the fields the request named. Read the fixed fields back once more, then stop and report any gap that remains.
